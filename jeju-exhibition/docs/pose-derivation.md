# 지화 포즈 클래스는 어떻게 나왔는가

`server/poseClasses.ts`는 손으로 쓴 파일이 아니다. 팀이 이미 찍어둔 실측 데이터에서 파생했다.
이 문서는 그 절차와 근거를 남긴다.

## 출발점: 왜 5비트를 버렸는가

ACC 버전은 손가락 5개의 접힘/펴짐을 5비트로 읽어 0~30을 자모 31개에 순서대로 배정했다
(`virtual-hand-rigged-final/server/binaryJamo.ts`). 손 모양과 자모 사이에 아무 관계가 없다.
관객이 만든 손은 지화처럼 보이지 않는다.

제주 버전은 실제 한글 지화를 쓴다. 그런데 여기서 물리적 한계에 부딪힌다.

## 한계: 리그에 손목이 없다

`robot_hand_rig.glb`를 열어보면 노드 29개, skin/bone/animation 없음. 순수 pivot 트랜스폼이다.

| 발견 | 결과 |
| --- | --- |
| 엄지 pivot이 `base`, `tip` 2개뿐 | 엄지 대립(opposition) 불가 |
| `palm_wrist`가 children=0인 메시 리프 | 손목 관절로 쓸 수 없다 |
| 벌림 전용 노드 없음 | base pivot을 2번째 축으로 돌려 흉내낸다 |
| 손 전체 방향 | 래퍼 group 회전으로만 가능 |

그리고 관객은 손가락 5개의 굽힘만 조종한다. 조종기가 5대이기 때문이다.

**한글 지화 모음 상당수는 손가락 모양이 같고 손 방향만 다르다.**
`ㅏ`/`ㅓ`, `ㅗ`/`ㅜ`가 대표적이다. 굽힘 5개 값만으로는 원리적으로 구분이 불가능하다.

## 선택: 모호함을 없애지 않고 남긴다

방향 자유도를 추가하는 대신, 구분되지 않는 자모를 **한 포즈의 여러 후보로 공존**시킨다.
그 손 모양이 `ㅏ`인지 `ㅓ`인지는 정하지 않고 LLM에 넘긴다.

이 선택은 전시 기획과 어긋나지 않는다. Notion 전시 방향성에 이렇게 적혀 있다.

> 관람객이 만든 형태가 사전적으로 틀렸더라도, AI는 그 속에 담긴
> '소통하고자 하는 인간의 의도'를 관대하게 해석해 줌.

부수 효과로 단어가 나올 확률이 오른다. 고정된 자모 6개로 단어를 만들라고 하면 억지가 되지만,
슬롯마다 선택지가 있으면 뜻이 통하는 조합을 고를 수 있다.

## 데이터: 이미 찍어둔 620개

`jamo-recognition/data/reference_samples.jsonl`에 실측 데이터가 있다.

```
31개 자모 x 20샘플 = 620개
MediaPipe 21 landmark, 2026-06-02 촬영
handedness: Left 600, Right 20
```

카메라 인식 경로용으로 모은 것이지만, 사람이 실제로 만든 지화 손 모양의 관절 좌표다.
지화 포즈를 추측할 필요가 없다.

## 절차

`scripts/analyze_poses.py`가 1~2단계를 한다.

### 1. 굽힘값 추출

손가락마다 관절 각도를 재고 0~100으로 사상한다. 로봇손 리그와 같은 규약을 쓴다(100=펴짐).

```
각 관절 각도: pi(펴짐) -> 1.0,  pi/2 이하(접힘) -> 0.0
손가락 굽힘 = 관절 점수 평균 x 100
```

관절 각도라서 손 크기나 카메라 거리에 영향받지 않고, 좌우손도 그대로 비교된다.

### 2. 구분 가능한 것끼리 묶기

관객이 제어하는 것은 굽힘 5개뿐이므로 **굽힘 거리만으로** 병합한다.
5차원 유클리드 거리가 임계값 미만인 자모를 같은 클래스로 합친다.

임계값을 22로 잡은 근거는 아래 스윕이다. 22~25 구간이 평탄해서 안정적이다.

| 임계값 | 클래스 수 | 최대 클래스 크기 |
| ---: | ---: | ---: |
| 5 | 27 | 3 |
| 15 | 24 | 3 |
| 18 | 21 | 5 |
| 20 | 19 | 6 |
| **22** | **17** | **6** |
| 25 | 17 | 6 |
| 30 | 13 | 6 |
| 35 | 10 | 18 |

같은 자모 안에서의 굽힘 표준편차는 2.5로 매우 작은데, 이 값을 임계값 근거로 쓰면 안 된다.
샘플이 0.25초 간격 연사라 손이 거의 움직이지 않은 상태의 분산이기 때문이다.
관객이 슬라이더로 재현할 때의 오차는 이보다 훨씬 크다.

결과는 17개 클래스다.

```
ㄱ/ㄴ/ㅏ/ㅗ/ㅜ/ㅡ   ㄷ/ㅅ/ㅈ/ㅑ/ㅛ/ㅠ   ㅐ/ㅚ/ㅟ/ㅢ   ㄹ/ㅌ
ㅁ  ㅂ  ㅇ  ㅊ  ㅋ  ㅍ  ㅎ  ㅒ  ㅓ  ㅔ  ㅕ  ㅖ  ㅣ
```

### 3. 도달 확률 균등화 — 이 단계가 없으면 전시가 망가진다

실측 포즈를 그대로 최근접 판정에 쓰면 5차원 공간의 가운데에 있는 포즈가 공간을 독점한다.
슬라이더 5개를 균등 무작위로 40만 번 굴려 확인한 결과다.

| | 점유율 |
| --- | ---: |
| ㅍ | 17.04% |
| ㅣ | 12.59% |
| ㅁ | 11.18% |
| ㅋ | 9.82% |
| … | |
| ㅊ | 0.96% |
| ㅂ | 0.82% |

**최대/최소 20.8배.** `ㅂ`과 `ㅊ`은 사실상 나오지 않고, 관객이 대충 움직이면
`ㅍ·ㅣ·ㅁ·ㅋ` 넷이 공간의 절반을 먹는다.

그래서 클래스마다 `bias`를 학습해 거리에서 뺀다. 목표 점유율은 1/17 = 5.88%.

```
d_i = ||handState - centroid_i|| - bias_i
선택 = argmin d_i
```

| | 보정 전 | 보정 후 |
| --- | ---: | ---: |
| 균등 분포 최대/최소 비 | 20.8배 | **1.0배** |
| U자 분포(관객이 끝까지 미는 경향) | 9.0배 | **2.2배** |
| 점유율 1% 미만 클래스 | 2개 | **0개** |

포즈 중심점은 실측 지화 그대로 두고 판정 경계만 옮기는 방식이라,
손 모양은 여전히 실제 지화를 향한다.

### 4. 벌림과 방향 프리셋

같은 데이터에서 손가락 벌림과 손 전체 방향도 뽑아 클래스마다 저장한다.
관객은 이것들을 제어하지 않는다. 렌더링에만 쓴다.

여러 자모가 든 클래스는 구성원들의 방향을 SVD로 평균 낸 값을 쓴다.

**단, 방향 프리셋은 현재 꺼져 있다**(`VirtualHand.tsx`의 `USE_POSE_ORIENTATION = false`).
손은 항상 정면 — 손등이 관객 쪽, 손가락이 위 — 을 향한다.

## 방향 프리셋을 왜 껐는가

`orientation` 값은 MediaPipe **카메라 좌표계**에서 뽑은 회전이다.
이것이 GLB의 three.js 좌표계에서 어느 축에 대응하는지는 알려진 바가 없다.
원본 캡처는 왼손 600개 / 오른손 20개가 섞여 있어 부호조차 확실하지 않다.

그대로 오일러각에 넣어보면 실제로 손이 정면을 크게 벗어난다.
예를 들어 `ㄹ/ㅌ` 클래스는 yaw -1.26rad(-72도), `ㅐ/ㅚ/ㅟ/ㅢ`는 -0.83rad(-47도)다.
그만큼 돌면 관객이 어느 손가락이 펴졌는지 읽을 수 없다.

자모의 모호함은 화면의 후보 칩("이 중 무엇인지는 아직 정해지지 않았다")이 이미 말해준다.
읽히지 않는 손으로 그것을 한 번 더 표현할 이유가 없다.

### 켜려면: 좌표계를 맞추는 절차

1. `USE_POSE_ORIENTATION = true`, `ORIENTATION_SCALE = 1`, `ORIENTATION_LIMIT = 3.2`로 둔다.
2. 방향이 확실한 자모 하나를 고른다. `ㅗ`(엄지 위)와 `ㅜ`(엄지 아래)가 좋다.
   같은 클래스에 있으므로 `perJamoOrientation`에서 개별 값을 꺼내 쓴다.
3. `ㅗ`를 적용하고 화면을 본다. 엄지가 위를 향해야 한다.
   아니라면 `applyOrientation`에서 yaw/pitch/roll을 어느 축에 넣을지 바꿔가며 맞춘다.
   (yaw→y, pitch→x, roll→z가 기본이고, 축 교환이나 부호 반전이 필요할 수 있다.)
4. `ㅜ`로 확인한다. `ㅗ`와 반대 방향이 나와야 한다. 같은 방향이면 부호가 뒤집힌 것이다.
5. `ㅏ`(오른쪽)와 `ㅓ`(왼쪽)로 나머지 한 축을 확인한다.
6. 맞으면 `ORIENTATION_SCALE`을 0.5~0.8로 줄이고 `ORIENTATION_LIMIT`을 다시 건다.
   실측 방향을 100% 적용하면 손이 뒤집혀 보인다.

캡처 데이터를 다시 찍는다면, 그때 카메라와 손의 기준 방향을 기록해두면
이 절차 자체가 필요 없어진다.

## 렌더링 원칙

**관객이 만든 굽힘값은 절대 건드리지 않는다.** 벌림과 방향만 클래스 프리셋으로 블렌딩한다
(`client/src/components/VirtualHand.tsx`).

가장 가까운 지화로 손을 스냅시키면 화면에는 항상 완벽한 지화가 뜬다. 그러면 기획서의 이 문장이 죽는다.

> 파편화된 개인들이 모여 완벽한 수화를 만드는 것은 불가능하며,
> 필연적으로 어설프고 기형적인 손 모양이 나옴.

## 재생성

```sh
cd GeSTure

```

임계값을 바꾸거나 reference sample을 다시 찍었다면 이 스크립트로 분석하고,
`server/poseClasses.ts`를 다시 생성한다.

## 검증: 찍어둔 데이터가 실제 표준 지화와 맞는가

표준 한글 지문자를 독립적으로 조사한 결과 3건과 실측 데이터를 자모별로 대조했다.

**결론: 31개 중 28개는 손 모양 패턴이 일치한다. 3개는 다시 찍는 것이 좋다.**

굽힘값의 절대 거리는 평균 77.6으로 커 보이지만 이것은 척도 차이다. 조사 쪽은 손가락을
0 아니면 100으로 이상화해 적었고, 실측 쪽은 관절 각도를 재기 때문에 "접힌" 손가락도
0이 아니라 40 근처로 나온다. 어느 손가락을 펴고 접는지의 **패턴**을 보는 상관계수는
평균 0.86이고, 대부분 0.95 이상이다.

패턴이 어긋나는 것은 셋뿐이다.

| 자모 | 상관 | 실측 | 표준 조사 | 같은 자모 내 표준편차 |
| --- | ---: | --- | --- | ---: |
| ㅁ | **-0.48** | 35 42 20 39 45 | 3 38 38 4 4 | 7.4 (2위) |
| ㅔ | **0.25** | 56 93 74 69 54 | 0 100 0 0 100 | 6.1 (4위) |
| ㅕ | **0.27** | 70 89 60 68 69 | 0 100 100 0 0 | 11.2 (1위) |

이 셋은 **같은 자모 안에서의 산포도 가장 큰 축에 속한다**(31개 중 1·2·4위).
촬영 당시 손 모양이 흔들렸거나 잘못 잡혔을 가능성이 높다. 표준과 어긋나는 것과
촬영이 불안정한 것이 같은 자모에서 겹치는 것은 우연으로 보기 어렵다.

이 셋을 다시 찍어 `reference_samples.jsonl`을 갱신하고 `analyze_poses.py`를 다시 돌리면
클래스 구성이 달라질 수 있다. 특히 `ㅔ`, `ㅕ`는 현재 각각 독립 클래스인데,
제대로 찍으면 다른 자모와 합쳐질 가능성이 있다.

## 손가락 좌우 벌림은 별도 영상에서 측정했다

포즈 클래스의 `abduction` 필드는 **쓰지 않는다**. 벌림은 굽힘에 연동해서 만든다.

### 왜 포즈 클래스 프리셋을 버렸는가

처음에는 클래스마다 실측 벌림 프리셋을 얹었다. 그런데 손을 쥐었다 폈다 할 때
벌어지는 방향이 실제 손과 반대로 보였다. 원인은 데이터였다.

```
굽힘 vs 벌림 상관   전체 -0.04
손가락별            엄지 +0.34, 검지 -0.16, 중지 -0.20, 약지 -0.38, 소지 -0.02
굽힘 구간별 평균     85.4 -> 81.5 -> 68.3 -> 70.3 -> 78.4  (단조롭지 않음)
```

`reference_samples.jsonl`은 31개 **정적 지화**를 찍은 것이다. 각 지화 고유의 벌림만
들어 있고, 손을 쥐고 펴는 동작 자체가 데이터에 없다. 없는 것을 회귀할 수는 없다.

### 측정

손 개폐 영상 63초를 따로 찍어서 썼다.

```
1620x1080, 30fps -> 10fps 프레임 630장 -> MediaPipe 검출 620장 (98%)
```

측정 방법은 `scripts/analyze_hand_video.py`에 있다. 세 가지가 중요했다.

**뿌리관절 첫 마디로만 잰다.** `tip - MCP`를 쓰면 손가락을 접었을 때 그 벡터가
손바닥 쪽을 향해 각도가 ±180도 근처로 뒤집힌다. 첫 시도에서 검지에 142도가 나왔다.
`MCP -> PIP`는 접어도 뿌리 관절의 좌우 방향을 그대로 유지한다.

**기준축을 손 자체에서 잡는다.** y는 손목에서 중지 MCP로, x는 검지 MCP에서 소지 MCP로
잡고 y와 직교화한다. 왼손/오른손, 손등/손바닥 어느 쪽에서 찍혔는지에 영향받지 않는다.

**네 손가락 평균을 뺀다.** 손을 접으면 네 손가락 각도가 다 같이 한쪽으로 25도쯤
이동한다. 손바닥 기준축이 함께 틀어져서 생기는 공통 오프셋이고 부채꼴과는 무관하다.

### 결과

| | 검지 | 중지 | 약지 | 소지 | 폭 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 펴짐 (n=183) | -6.6° | -1.0° | +0.9° | +6.7° | **13.3°** |
| 접힘 (n=25) | -2.4° | +1.2° | +1.9° | -0.7° | **4.3°** |

부채꼴 폭이 **13.3도에서 4.3도로 줄어든다**(수축비 0.33). 손을 쥐면 손가락이 모인다.

펴짐 구간은 표본이 183장이고 검지에서 소지로 단조롭게 벌어진다. 접힘 구간은 25장뿐이라
순서가 흔들려서(소지가 -0.7로 검지 쪽), 부채꼴 **모양은 펴짐 것을 쓰고 폭만 0.33배로**
줄였다. 엄지는 부채꼴이 아니라 손바닥에서 벌어졌다 붙었다 하므로 변화량 10.2도만
쓰고 중앙에 맞췄다.

측정 부호(양수 = 소지쪽)와 GLB 리그의 y축 부호가 반대라 뒤집어 넣었다.
축과 방향은 값을 3배로 과장해 렌더링해서 확인했다. 좌우 부채꼴이 맞고 비틀림이 아니다.

### 다시 측정하려면

```sh
ffmpeg -i 영상.mov -vf "fps=10,scale=1080:-1" -q:v 2 frames/f%05d.jpg
.venv/bin/python jeju-exhibition/scripts/analyze_hand_video.py frames/
```

촬영 조건: 손 전체가 프레임에 들어오고, 카메라와의 거리가 일정하고, **손목을 돌리지 않는다.**
손목이 함께 돌면 벌림과 회전이 섞여 분리되지 않는다. 지화를 만들 필요는 없고
주먹에서 완전히 펴기를 천천히 반복하면 된다. 접힘 구간 표본이 부족하지 않도록
접은 상태에서 잠시 멈춰 주는 편이 좋다.
